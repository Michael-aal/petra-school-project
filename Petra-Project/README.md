
# Petra School System · Frontend

The frontend for **Petra School System**, a modern school management platform designed to bring student records, academics, attendance, communication, finance, and parent services into one unified dashboard experience.

Built with **React + Vite**, the frontend provides role-based interfaces for school administrators, staff, parents, and learners while connecting to the Petra backend through dedicated API services.

---

## Overview

Petra is designed around a simple idea:

> One school system, one source of truth.

The frontend provides focused workflows for managing and viewing school data without forcing every user through the same interface.

Current areas include:

- Parent portal
- Student management
- Staff management
- Staff attendance
- Student attendance
- Examination and results
- Report cards
- School fees and payments
- Enrollment
- Sessions and academic terms
- Notifications
- Messaging
- School profile and settings
- Dashboard analytics
- Authentication and registration flows

## Design System

Petra follows a deliberate visual system rather than the default styling generated by the framework.

### 60 / 30 / 10 visual balance

**60% White**

Primary content surfaces, cards, forms, tables, and workspace areas.

**30% Deep Navy**

Structural elements such as the dashboard sidebar and major navigation surfaces.

**10% Electric Blue**

Primary actions, active navigation, links, focus states, selected states, and important interface highlights.

## API Architecture

Frontend API access is organized into dedicated service modules instead of scattering raw `fetch()` calls throughout page components.

Examples include:

```js
import { parentApi } from "./services/parentApi";
```

```js
parentApi.children();
parentApi.child(studentId);
parentApi.childHub(studentId);
```

Finance-related functionality follows the same service-oriented approach:

```js
financeApi.parentFees();
financeApi.createPayment(payload);
```

This keeps UI components focused on presentation and interaction while API services handle communication with the backend.

## Styling Guidelines

When adding or modifying frontend styles:

1. Prefer page-scoped selectors.

```css
.settings-page .settings-button {
  /* styles */
}
```

2. Use the Petra design tokens where possible.

```css
background: #ffffff;
color: #10233f;
border-color: #e2e8f0;
```

3. Use electric blue for primary interaction.

```css
background: #2563eb;
```

4. Use deep navy for structural navigation.

```css
background: #0f2747;
```

5. Reserve red for errors and destructive actions.

```css
color: #dc2626;
```

6. Avoid reintroducing legacy orange, teal, or unrelated theme systems.

7. Avoid broad selectors that can unintentionally modify unrelated pages.

## Development Principles

### Keep business logic out of presentation where possible

Components should coordinate UI state and user interactions while reusable API and utility logic stays in dedicated modules.

### Preserve existing workflows

Visual changes should not alter:

* API routes
* Authentication flows
* Payment workflows
* Database contracts
* Existing navigation behavior

### Prefer reusable components

Common dashboard elements should use shared components such as:

```text
DashboardHeader
StatCard
DashboardWidget
QuickActions
EmptyState
```

This keeps the interface consistent as Petra expands.

### Keep CSS predictable

Avoid stacking multiple "final override" blocks to fix earlier CSS. One authoritative style is easier to debug than six layers of historical evidence.
